# AI 执行指南

根目录 `AGENTS.md` 规定通用协作和执行方式；本文保留小鱼精灵特有的架构、API 设计和
文档同步边界，不维护完整 API 清单。当前能力以
[统一 API 契约](contracts/API_契约.md)、[公开脚本文档](../public/脚本文档.md)、源码和测试
为准。

## 开始任务

1. 从 [`docs/README.md`](../README.md) 判断任务属于全局架构、Android、IDE 工具、脚本 API
   还是构建发布。
2. 检查 Git 状态，保留用户已有修改，不把其他任务的改动一起清理。
3. 阅读对应契约、平台说明和模块 `README.md`，再查看实际源码与测试。
4. 如果文档和实现冲突，先用代码与测试确认真实行为，再修正所有受影响的现行文档。

不要求后续 AI 取得历史聊天记录。会影响长期维护的讨论结论必须写入对应的代码注释、内部契约、
架构或平台文档。

## 架构原则

- 未完成或实验能力可以保留内部 C ABI、扩展开发资料和带状态的公开说明，但不能写成脚本
  已可直接依赖的稳定能力。
- 新增语言无关脚本 API 时，先做 `libengine.so/core/api` 核心实现。
- `system_c_api` 只做 C ABI 门面，不写最终业务逻辑。
- Lua / JS / Go 绑定层只做参数转换和返回值封装。
- 语言自身的运行时语义放在对应 `runtime/<语言>`；Lua 多线程不伪装成通用 C ABI。
- 动态 Java 对象属于语言互操作能力，不为每个 Java 方法制造固定 C ABI。
- IDE 工具与 Android 可复用的图像算法优先进入 `shared/native/image_core`。
- 旧的系统自动化入口不要从历史代码恢复；需要时按当前边界重新设计和实现。

## Android 脚本 API 设计基线

- 新增 Android 脚本能力前，先核对懒人精灵和触动精灵的公开文档，以及本项目的现有契约、
  源码和测试。
- 两者的接口约定一致或可直接兼容时，函数名、参数顺序、可选参数、默认值、返回值和失败
  语义默认沿用；Lua `m.*` 绑定优先保持这种兼容性。
- 如果两份文档存在实质差异，结合兼容性、清晰度和长期稳定性选择更优的一方，也可以都不
  采用；只有需要采用明显更优的新方案时，才先向用户说明对比和理由。
- `_host` 是内部实现，不受第三方函数名和 `m.*` 命名约束。
- 选择 Android 系统接口时，先参考较新的老项目实现；只有较新项目不足以判断时才查看旧项目。
  不要把老项目的兼容分支或内部协议直接混入当前实现。
- 在后续统一兼容层设计完成前，不扩展或重定义 `lr`、`cd` 的兼容内容；以后按各自来源统一处理。
- 设计核对完成后，把最终真实行为写入内部 API 契约、公开函数页、API 总览和
  `catalog.json`；外部文档不能替代本项目的权威资料。

## 文档同步

- 脚本 API 变化：同步内部 API 契约、公开函数页、API 总览和 `catalog.json`。
- 公开脚本文档的分类顺序由 `catalog.json` 顶层 `order` 控制；交互式目录中的高频命令顺序由
  `脚本文档.html` 的 `COMMAND_ORDER` 维护。新增常用能力时同步放入对应的使用流程，不按文件名
  或新增时间机械追加。
- 分类节点如果有自己的概述页，应把它作为 `items` 的第一项；父节点只负责展开分类，不要同时
  再挂同一份 `md`，避免概述显示在分类外层。
- IDE 工具工作流变化：同步行为契约和工具说明；纯视觉调整不虚构业务变化。
- 架构或发布边界变化：更新对应的架构、平台说明、契约和文档总入口。
- `docs/public/` 是发布白名单；内部实现说明和归档资料不得自动发布。
- 长清单只保留在一个权威位置，其他文档用链接引用，避免功能增加后出现过期副本。

## 验证与交付

- 验证范围与风险相称；纯文档整理运行文档检查，普通小幅界面调整不必每次运行整套测试。
- 涉及核心状态、并发、协议、文件保存或算法时，运行对应测试；用户明确要求编译时再编译。
- 编译遇到输出文件被占用时直接说明，可能是用户另一台电脑正在使用；允许由用户自行编译。
- 只有用户明确要求时才创建提交；不要自动推送远程仓库。
