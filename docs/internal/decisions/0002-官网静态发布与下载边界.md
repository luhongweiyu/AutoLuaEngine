# 0002：官网静态发布与下载边界

- 状态：已接受
- 日期：2026-07-27

## 背景

项目需要一个便于宣传、部署简单且不会意外公开源码和内部实现资料的官网。用户已有自己的
静态网页服务器，安装包可以由 GitHub 承担版本管理和下载，不需要为官网引入服务端应用、
数据库或额外的下载系统。

项目规划面向 JavaScript、Lua、Go 和 PC、Android、iOS，但第一阶段真实实现仍聚焦
Android + Lua。宣传需要表达完整方向，同时不能把未完成能力描述成已经可用。

## 决定

1. 以 `docs/public/` 作为官网唯一发布根目录，部署时保持目录内相对路径不变。
2. `docs/public/index.html` 是无构建依赖的纯静态宣传首页；样式与交互内置在 HTML 中，
   图片等二进制资源放在 `docs/public/assets/`。
3. `docs/public/脚本文档.html` 继续作为用户文档应用，并按需读取同目录下的目录数据和
   Markdown 正文。
4. 官网负责产品定位、IDE 工具、三种语言与三端平台的整体范围，以及文档和下载入口；
   具体可用能力与版本进度统一由脚本文档和 GitHub Releases 说明。
5. 如果源码仓库不公开，可以使用独立的公开发布仓库承载 Releases；官网和发布仓库都不得
   自动带出 `docs/internal/`、`docs/archive/` 或源码实现资料。
6. 宣传页按长期产品定位展示 JavaScript、Lua、Go 与 PC、Android、iOS，不在首页维护
   阶段状态矩阵，也不直接断言所有能力已经完成；具体可用范围、参数和兼容性以脚本文档
   与 GitHub Releases 为准。

## 后果

- 官网可以直接复制或同步 `docs/public/` 到用户自己的静态服务器，不需要 Node、数据库或
  服务端运行环境。
- 文档应用不是单一文件；发布时仍需同步完整的 `docs/public/脚本文档/` 目录。
- 安装包更新与官网内容更新相互独立，后续发布脚本可以分别更新 GitHub Releases 和静态目录。
- 新语言或新平台形成可用闭环时，需要同步核对源码、内部计划、公开能力文档和
  GitHub Releases；只有产品定位或官网信息架构改变时才需要修改宣传首页。
